# Human Test Checklist: Incremental Update Mode (`dazzlesum update`)

**Target version:** 1.4.0
**Ships with commit:** TBD (branch `feature/update-mode`)
**Companion automated tests:** 21 tests in `tests/test_update_mode.py` (semantics, bootstrap, scoping, shadow-dir, StateCache unit), plus updated `tests/test_cli.py::test_update_subcommand_help`

## What this is

`dazzlesum update` previously accepted an `update_mode` parameter that was never read -- it silently performed a full re-hash of everything. v1.4.0 makes it real: a per-machine SQLite state cache records each file's (size, mtime) at last hash, and update rehashes only files whose current stat differs from the recorded state. This checklist is the human companion to the automated suite: it verifies terminal rendering, real-scale behavior, interruption safety, and UX quality that mocks cannot. Anyone with Python 3.8+ and a copy of this repo can run it.

## Prerequisites

1. Python 3.8+ with `pytest` (for the pre-flight step only).
2. This repo checked out at the commit under test; run commands from the repo root.
3. All tests below operate in a throwaway directory you create; **nothing touches your real data** except the clearly marked, opt-in Section 3 (real-library benchmark).
4. Invocation used throughout (all shells): `python dazzlesum.py ...` from the repo root. Substitute `python3` on POSIX if needed.

**Create the sandbox** (pick your shell):

**cmd.exe**:
```cmd
set SBOX=%TEMP%\dzsum-checklist
if exist "%SBOX%" rmdir /s /q "%SBOX%"
mkdir "%SBOX%\data\sub"
echo alpha> "%SBOX%\data\a.txt"
echo bravo> "%SBOX%\data\b.txt"
echo charlie> "%SBOX%\data\sub\c.txt"
```

**PowerShell**:
```powershell
$env:SBOX = "$env:TEMP\dzsum-checklist"
if (Test-Path $env:SBOX) { Remove-Item -Recurse -Force $env:SBOX }
New-Item -ItemType Directory -Force "$env:SBOX\data\sub" | Out-Null
Set-Content "$env:SBOX\data\a.txt" "alpha"
Set-Content "$env:SBOX\data\b.txt" "bravo"
Set-Content "$env:SBOX\data\sub\c.txt" "charlie"
```

**POSIX**:
```bash
export SBOX=/tmp/dzsum-checklist
rm -rf "$SBOX"; mkdir -p "$SBOX/data/sub"
echo alpha > "$SBOX/data/a.txt"
echo bravo > "$SBOX/data/b.txt"
echo charlie > "$SBOX/data/sub/c.txt"
```

**Reset between sections**: re-run the sandbox creation block above. It deletes and rebuilds everything, including the state cache.

**Pre-flight** (cross-shell, from repo root):
```
python -m pytest tests/test_update_mode.py -q
```
Expect: `21 passed`. If this fails, stop -- the automated layer is broken and manual testing is premature.

## High-Value Verification (~5 minutes)

If you only have 5 minutes, run these 6. All commands assume the sandbox exists and you are in the repo root.

### HV.1 -- Update is actually incremental now

Validates: the headline feature -- second run does zero hashing.

- [ ] **Steps** (cross-shell; `%SBOX%` on cmd, `$env:SBOX` on PowerShell, `$SBOX` on POSIX -- shown as `<SBOX>` below):
  1. `python dazzlesum.py update -r <SBOX>/data`
  2. `python dazzlesum.py update -r <SBOX>/data` (again)
- [ ] **Expected:** First run's final line reports `3 rehashed`; second run reports `3 unchanged, 0 rehashed, ... 0 manifests rewritten` and finishes near-instantly.
- [ ] **Why this matters:** If the second run rehashes, the cache layer isn't engaged and v1.4.0's entire purpose is missing.

### HV.2 -- The Resilio case: older mtime, changed content

Validates: stat-EQUALITY detection (not "mtime newer"), the design's load-bearing decision.

- [ ] **Steps** (cross-shell via Python one-liner, run after HV.1):
  1. ```
     python -c "import os,sys; p=os.path.join(os.environ.get('SBOX') or '/tmp/dzsum-checklist','data','a.txt'); st=os.stat(p); open(p,'w').write('omega\n'); old=st.st_mtime_ns-3600*10**9; os.utime(p, ns=(old,old))"
     ```
  2. `python dazzlesum.py update -r <SBOX>/data`
- [ ] **Expected:** `1 rehashed`, `1 manifests rewritten`. The change is caught even though the file's mtime moved BACKWARD.
- [ ] **Why this matters:** Synced trees (Resilio) deliver content with origin mtimes older than the local scan; a "newer-than" implementation silently misses those changes forever.

### HV.3 -- Trust-bootstrap against pre-existing manifests

Validates: adopting an existing manifest tree without rehashing (the 166K-manifest library scenario).

- [ ] **Steps:**
  1. Delete the cache: `del "%SBOX%\data\.dazzle-cache.sqlite"` (cmd) / `Remove-Item "$env:SBOX\data\.dazzle-cache.sqlite"` (PowerShell) / `rm "$SBOX/data/.dazzle-cache.sqlite"` (POSIX)
  2. `python dazzlesum.py update -r --bootstrap trust <SBOX>/data`
- [ ] **Expected:** Instant completion, `3 unchanged, 0 rehashed`. Cache file reappears.
- [ ] **Why this matters:** Without trust-bootstrap, adopting an existing library means one full multi-hour rehash before incrementality begins.

### HV.4 -- `--dirs-from` scoping

Validates: the external-change-detector adapter (git hooks, watchers).

- [ ] **Steps:**
  1. Modify both files: append text to `<SBOX>/data/a.txt` AND `<SBOX>/data/sub/c.txt` (any editor or `echo more>> file`)
  2. Feed only `sub` via stdin: `echo sub| python dazzlesum.py update -r --dirs-from - <SBOX>/data`
- [ ] **Expected:** `1 dirs ... 1 rehashed` -- only `sub` was touched; root's change remains pending until a full sweep.
- [ ] **Why this matters:** This flag is the integration point for every future detection source; if scoping leaks, hint-driven updates are untrustworthy.

### HV.5 -- Unchanged manifests stay byte-identical

Validates: no git churn / no needless rewrites.

- [ ] **Steps** (after a full `update -r` so everything is current):
  1. Record the manifest's timestamp: `dir "%SBOX%\data\.shasum"` (cmd) / `(Get-Item "$env:SBOX\data\.shasum").LastWriteTime` (PowerShell) / `stat "$SBOX/data/.shasum"` (POSIX)
  2. `python dazzlesum.py update -r <SBOX>/data`
  3. Check the timestamp again.
- [ ] **Expected:** Timestamp identical; report shows `0 manifests rewritten`.
- [ ] **Why this matters:** For version-controlled shadow trees, every gratuitous rewrite is diff noise and a destroyed "last real change" signal.

### HV.6 -- Help discoverability

Validates: a new user can find and understand the feature.

- [ ] **Steps:**
  1. `python dazzlesum.py update --help`
  2. `python dazzlesum.py --detailed-help update`
- [ ] **Expected:** (1) lists `--dirs-from`, `--bootstrap`, `--paranoid`, `--keep-missing` with meaningful one-liners; (2) prints the full semantics page (cache warning, per-file semantics table, exit codes).
- [ ] **Why this matters:** An undiscoverable feature ships as dead weight; this is also where the "never sync the cache" warning lives.

## Section 1: Update semantics, end to end (~10 min)

Reset the sandbox first.

### 1.1 First run creates manifests + cache

- [ ] **Steps:** `python dazzlesum.py update -r <SBOX>/data`
- [ ] **Expected:** Report: `2 dirs ... 3 rehashed, 3 added, ... 2 manifests rewritten`.
- [ ] **Check:** `<SBOX>/data/.shasum`, `<SBOX>/data/sub/.shasum`, and `<SBOX>/data/.dazzle-cache.sqlite` all exist. View a manifest (`type`/`Get-Content`/`cat`): header comment, `hash  filename` lines, `# End of checksums` -- and NO entry for `.dazzle-cache.sqlite` or `.shasum` itself.

### 1.2 Added file

- [ ] **Steps:** Create `<SBOX>/data/new.txt` with any content; run update.
- [ ] **Expected:** `1 rehashed, 1 added, 1 manifests rewritten`; `new.txt` appears in `<SBOX>/data/.shasum`.

### 1.3 Deleted file (default: drop)

- [ ] **Steps:** Delete `<SBOX>/data/new.txt`; run update.
- [ ] **Expected:** `1 removed, 1 manifests rewritten`; entry gone from the manifest.

### 1.4 Deleted file with `--keep-missing`

- [ ] **Steps:** Delete `<SBOX>/data/b.txt`; run `python dazzlesum.py update -r --keep-missing <SBOX>/data`.
- [ ] **Expected:** `0 removed`; `b.txt` STILL listed in the manifest with its old hash.
- [ ] **Check:** `python dazzlesum.py verify -r <SBOX>/data` now reports `b.txt` as MISSING -- the preserved entry keeps the signal alive. (Restore `b.txt` afterward or reset.)

### 1.5 Touched but unchanged (mtime bump, same content)

- [ ] **Steps:**
  1. ```
     python -c "import os,time; p=os.path.join(os.environ.get('SBOX') or '/tmp/dzsum-checklist','data','a.txt'); os.utime(p)"
     ```
  2. Run update twice.
- [ ] **Expected:** First run: `1 rehashed` but `0 manifests rewritten` (hash confirmed identical, manifest untouched). Second run: `0 rehashed` (cache learned the new mtime).

### 1.6 Tampered manifest self-heals

- [ ] **Steps:** Open `<SBOX>/data/.shasum` in an editor and corrupt one hash (change a few hex chars). Run update.
- [ ] **Expected:** At least `1 rehashed`, `1 manifests rewritten`, and the manifest now shows the correct hash again.

### 1.7 `--paranoid` full rehash

- [ ] **Steps:** `python dazzlesum.py update -r --paranoid <SBOX>/data`
- [ ] **Expected:** Every file rehashed (`rehashed` == file count), `0 manifests rewritten` (content already correct).

## Section 2: Cache behavior (~5 min)

### 2.1 Shadow-dir placement

- [ ] **Steps:** Reset sandbox, then `python dazzlesum.py update -r --shadow-dir <SBOX>/shadow <SBOX>/data`
- [ ] **Expected:** Manifests appear under `<SBOX>/shadow/` (mirroring the tree); `.dazzle-cache.sqlite` is at `<SBOX>/shadow/`, NOT in `<SBOX>/data/`; the source tree contains no dazzlesum files at all.

### 2.2 Cache is disposable

- [ ] **Steps:** Delete the cache file; run update with `--bootstrap trust`; run update again plain.
- [ ] **Expected:** No errors; second run `0 rehashed`. Deleting the cache never loses checksum data -- manifests are the record.

### 2.3 Cache never gets checksummed

- [ ] **Steps:** After 2.1/2.2, inspect all `.shasum` files for `dazzle-cache` (cmd: `type ...\.shasum | findstr dazzle-cache`; PowerShell: `Select-String dazzle-cache <file>`; POSIX: `grep dazzle-cache <file>`).
- [ ] **Expected:** No matches anywhere, including SQLite `-journal` sidecars.

### 2.4 Version-control hygiene note (read, then verify locally if applicable)

- [ ] If your shadow tree is under git: confirm `.dazzle-cache.sqlite*` is either gitignored or untracked before committing. The cache is per-machine state -- committing or syncing it poisons other machines' change detection. (dazzlesum cannot enforce this; it's an operator responsibility. The detailed help warns about it.)

## Section 3: Real-library scale (OPT-IN; maintainers with the D:\M library only)

**Skip this section** unless you are on a machine hosting the ~166K-manifest research library AND its checksum baseline is fully committed AND no other process (git staging, Resilio indexing) is hammering the disk.

### 3.1 Trust-bootstrap the baseline (one-time)

- [ ] **Steps** (PowerShell; mirror the library wrapper's exclusions):
  ```powershell
  python C:\code\dazzlesum\dazzlesum.py update -r --bootstrap trust `
    --shadow-dir D:\M\STRL\Checksums `
    --exclude .sync --exclude .git --exclude .private --exclude .claude `
    --exclude __pycache__ --exclude STRL --exclude .vscode  D:\M
  ```
- [ ] **Expected:** Completes WITHOUT hashing (stat + manifest reads only); report shows `unchanged` in the ~150K-file range, `0 rehashed` (or a small number if files genuinely changed since the baseline scan). Note the elapsed time: ______
- [ ] **Why:** Seeds the cache from the committed baseline so all future updates are incremental.

### 3.2 Steady-state sweep benchmark (design acceptance AC-10)

- [ ] **Steps:** Re-run the same command without `--bootstrap trust`.
- [ ] **Expected:** `0 rehashed` (unchanged library), single-digit **minutes** wall time. Record: dirs ______, elapsed ______s.
- [ ] **Target:** >= 10x faster than a full create (which takes hours on this library). If it's not, file an issue with the numbers.

### 3.3 Hint-driven spot update

- [ ] **Steps:** Touch one file somewhere in the library (e.g. re-save a README), then feed just its folder:
  ```powershell
  "Literature/Books" | python C:\code\dazzlesum\dazzlesum.py update -r --dirs-from - `
    --shadow-dir D:\M\STRL\Checksums D:\M
  ```
  (adjust the folder to where you touched the file)
- [ ] **Expected:** Completes in seconds; only the nominated folder is examined.

## Section 4: Terminal rendering & platform (~5 min)

### 4.1 Windows cmd.exe codepage

- [ ] **Steps:** Run HV.1 from a plain `cmd.exe` window (not Windows Terminal, if available).
- [ ] **Expected:** No mojibake, no `UnicodeEncodeError`, no garbled box characters -- all update output is plain ASCII. Stats line wraps sanely at 80 columns.

### 4.2 Interruption mid-run (atomicity spot check)

- [ ] **Steps:**
  1. Build a bigger sandbox (cross-shell): `python -c "import os; root=os.path.join(os.environ.get('SBOX') or '/tmp/dzsum-checklist','big'); [open(os.path.join(root,d,'f%d.bin'%i),'wb').write(os.urandom(300000)) for d in [os.makedirs(os.path.join(root,'d%02d'%n),exist_ok=True) or 'd%02d'%n for n in range(40)] for i in range(20)]"`
  2. Run `python dazzlesum.py update -r <SBOX>/big` and press **Ctrl-C** partway through.
  3. Search for leftovers: any `.shasum.tmp` files under `<SBOX>/big`? (cmd: `dir /s /b "%SBOX%\big\*.tmp"`; PowerShell: `Get-ChildItem -Recurse -Filter *.tmp $env:SBOX\big`; POSIX: `find "$SBOX/big" -name "*.tmp"`)
  4. Run the update again to completion, then once more.
- [ ] **Expected:** (3) No `.tmp` leftovers, and every existing `.shasum` parses (header + entries + end marker -- spot-check one). (4) Final run reports `0 rehashed`: the interrupted run's completed work was preserved, the rest was picked up cleanly.

### 4.3 Error paths read sensibly

- [ ] **Steps:** Try each; judge the messages as a user:
  1. `python dazzlesum.py update -r --dirs-from missing.txt <SBOX>/data` (nonexistent list file)
  2. Put an outside path (e.g. `C:\Windows` or `/etc`) in a dirs file and run with it.
- [ ] **Expected:** (1) Clear "cannot read" error, exit code 1, no traceback. (2) `Skipping ...: not under ...` warning; run continues; exit 0.

## What the automated tests DON'T cover

- Real terminal rendering on Windows codepages (cmd.exe 437 / PowerShell 1252)
- True Ctrl-C interruption (tests can't deliver a mid-write SIGINT reliably cross-platform)
- 166K-manifest scale: wall-clock feel, SQLite performance at 500K rows, disk contention
- Whether stats output, flag names, and help text are *understandable*, not just present
- Version-control hygiene around the cache file (operator behavior, not code)
- Cross-platform runs (suite runs on the dev box; POSIX behavior verified in CI only after push)

**HV.4 finding (the checklist earning its keep):** piping `"sub"` from PowerShell delivered a UTF-8 BOM (EF BB BF) on stdin; Python's default cp1252 stdin decoding mangled it into junk prepended to the first folder name, which was then skipped as "not a directory" -- silently, with `0 dirs` the only symptom. The automated tests passed because they called `run_update()` below the CLI layer. Fixed by reading stdin as bytes and decoding `utf-8-sig` (files already used `utf-8-sig`); two CLI-layer regression tests added (`TestDirsFromParsing`). This failure mode is invisible to mocks by construction.
