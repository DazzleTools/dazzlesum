# Human Test Checklist: v1.5.0 src/ Split Ship-Readiness

**Target version:** 1.5.0 (final; validates the 1.5.0-alpha.3 through 1.5.0-alpha.7 refactor line)
**Ships with commit:** v1.5.0-alpha.7: Fix native-tool detection; UNC layer via filekit (merge of `phase1-src-split`)
**Companion automated tests:** 135 tests across 11 files, run against BOTH targets (package and stitched artifact): tests/test_update_mode.py (35), tests/test_cli.py (19), tests/test_squelch_and_grand_totals.py (15), tests/test_basic.py (14), tests/test_verbosity_system.py (13), tests/test_shadow_directory.py (12), tests/test_monolithic_autodetection.py (8), tests/test_monolithic_verification.py (6), tests/test_verify_integration_autodetection.py (5), tests/test_junction_detection.py (4), tests/test_versioning.py (4). Plus 13 one-off scripts under tests/one-offs/.

## What this is

Ship-readiness verification for the v1.5.0 structural refactor: the monolithic `dazzlesum.py` became a `src/dazzlesum/` package with a build-time stitched single-file artifact, the DazzleLib stack (`dazzle-lib`, `dazzle-filekit`) became hard dependencies, and two long-standing silent failures were fixed (native checksum-tool detection, dead UNC integration). A human runs this before the v1.5.0 release is tagged and published to PyPI. The performance work in 1.5.0-alpha.1/.2 (7.4x engine) was validated separately -- see `v1.4.4__Epic__snappy-update-verification.md` -- and is only smoke-checked here.

## Prerequisites

1. Windows 10/11 with Python 3.9+ (primary target); optionally a POSIX box for cross-platform items
2. This repo checked out at the commit under test, working tree clean apart from the checklist run
3. `pip install dazzle-lib>=0.6.7 dazzle-filekit>=0.3.2` available (normal environment); ability to create a **bare venv without them** for the self-containment tests
4. A scratch fixture directory -- all steps below use the OS temp dir, never real data
5. If `dz safedel` is installed, use it for cleanup deletions; otherwise the plain deletes shown are limited to the scratch tree
6. **cwd caveat for the `python -c "import dazzlesum ..."` checks** (HV.1, HV.3, HV.5, 1.3): do NOT run them from the repo root. The root-level stitched `dazzlesum.py` shadows the installed src/ package when the current directory is the repo root, so you would silently test the artifact while believing you tested the package. Run them from the scratch directory (or any directory outside the repo) with the package installed, e.g. `cd %SHIPCHK%` first. Steps that invoke `dazzlesum.py` BY PATH (HV.2, Section 2) are unaffected -- shadowing is exactly what those steps want.

**Fixture setup** (pick your shell):

**cmd.exe**:

## High-Value Verification (~5 minutes)

**If you only have 5 minutes**, run these 6. They cover the refactor's load-bearing claims. If any fail, the release is broken.

### HV.1 -- Package imports and reports the right version

Validates: the src/ split produced an importable package with working dynamic-version packaging (the alpha.4 packaging fix).

- [ ] **Steps** (same across all shells):
  ```
  python -c "import dazzlesum; print(dazzlesum.__version__)"
  ```
- [ ] **Expected:** A `1.5.0...` version string; no ImportError, no traceback from the dazzle-lib/filekit imports.
- [ ] **Why this matters:** If the package can't import or the version attr fails, pip installs of v1.5.0 are dead on arrival.

### HV.2 -- Stitched artifact is genuinely self-contained

Validates: the single-file `dazzlesum.py` runs with NO DazzleLib stack installed (the artifact doctrine: vendored objects + self-contained snippets, zero runtime lib imports).

- [ ] **Steps** (PowerShell shown; same shape elsewhere):
  ```powershell
  python -m venv "$env:SHIPCHK\bare-venv"
  & "$env:SHIPCHK\bare-venv\Scripts\python.exe" dazzlesum.py --version
  & "$env:SHIPCHK\bare-venv\Scripts\python.exe" dazzlesum.py create "$env:SHIPCHK\vault" -r
  ```
  **POSIX**:
  ```bash
  python -m venv "$SHIPCHK/bare-venv"
  "$SHIPCHK/bare-venv/bin/python" dazzlesum.py --version
  "$SHIPCHK/bare-venv/bin/python" dazzlesum.py create "$SHIPCHK/vault" -r
  ```
- [ ] **Expected:** Version prints; create walks the fixture and writes `.shasum` files in `vault\alpha` and `vault\beta`. No ModuleNotFoundError for `dazzle_filekit` / `dazzle_lib` / `unctools`.
- [ ] **Why this matters:** Self-containment is the artifact's entire reason to exist -- a lib import that leaked through the stitcher breaks every no-deps user.

### HV.3 -- Native tool detection finds a REAL tool (the U4 fix)

Validates: `_tool_available` reads both output streams and ignores exit codes, against the real certutil (Windows) or shasum/md5sum (POSIX) -- not a mock.

- [ ] **Steps** (Windows, same across shells):
  ```
  python -c "from dazzlesum.hashing import DazzleHashCalculator; c = DazzleHashCalculator(); print(c._tool_available('certutil'))"
  ```
  **POSIX**:
  ```bash
  python -c "from dazzlesum.hashing import DazzleHashCalculator; c = DazzleHashCalculator(); print(c._tool_available('shasum'))"
  ```
- [ ] **Expected:** `True` on any stock Windows box (certutil ships with the OS) / any box with shasum. Before the fix this printed `False` everywhere -- the bug forced pure-Python hashing on every machine tested.
- [ ] **Why this matters:** This is the exact real-subprocess divergence mocks missed for months; only a human on a real box proves it.

### HV.4 -- Dual-target automated gate is green

Validates: the full suite passes against BOTH import targets.

- [ ] **Steps**:

  **cmd.exe**:
  ```cmd
  python -m pytest tests -q
  set DAZZLESUM_TEST_TARGET=stitched
  python -m pytest tests -q
  set DAZZLESUM_TEST_TARGET=
  ```

  **PowerShell**:
  ```powershell
  python -m pytest tests -q
  $env:DAZZLESUM_TEST_TARGET = "stitched"
  python -m pytest tests -q
  Remove-Item Env:\DAZZLESUM_TEST_TARGET
  ```

  **POSIX**:
  ```bash
  python -m pytest tests -q
  DAZZLESUM_TEST_TARGET=stitched python -m pytest tests -q
  ```
- [ ] **Expected:** 148 passed (135 core + 13 one-off scripts), 0 failed, on both runs.
- [ ] **Why this matters:** The refactor's core promise is that package and artifact behave identically; a single-target pass proves half of it.

### HV.5 -- UNC layer is genuinely wired (not silently dead again)

Validates: the filekit delegation is live -- the failure mode being guarded is precisely "optional layer looks fine but never runs."

- [ ] **Steps** (same across all shells):
  ```
  python -c "import dazzlesum; print(dazzlesum.HAVE_UNCTOOLS, dazzlesum.is_unc_path(r'\\\\server\\share\\x'), dazzlesum.is_unc_path('C:/x'), hasattr(dazzlesum, 'normalize_path'))"
  ```
- [ ] **Expected:** `True True False False` -- layer wired, UNC path recognized, drive path not, `normalize_path` gone from the surface.
- [ ] **Why this matters:** The unctools integration was dead for months without a single test noticing; this proves the replacement actually executes.

### HV.6 -- End-to-end roundtrip through the installed console script

Validates: `[project.scripts] dazzlesum = "dazzlesum:main"` resolves post-split, and create -> verify roundtrips.

- [ ] **Steps** (PowerShell shown):
  ```powershell
  pip install -e . --quiet
  dazzlesum create "$env:SHIPCHK\vault" -r
  dazzlesum verify "$env:SHIPCHK\vault" -r
  ```
- [ ] **Expected:** create writes `.shasum` per folder; verify reports all files OK, exit code 0 (`echo %ERRORLEVEL%` / `$LASTEXITCODE` / `echo $?`).
- [ ] **Why this matters:** The console-script entry point is what every pip user actually types; a bad entry-point string ships a package that installs but cannot run.

## Section 3: Real native-tool behavior (~10 min, Windows-focused)

### 3.1 Engine selection is Python-first, and digests are independently correct

- [ ] **Steps** (PowerShell; note the log stream is stderr, so merge it before filtering):
  ```powershell
  dazzlesum create "$env:SHIPCHK\vault\alpha" -vvvv 2>&1 | Select-String -Pattern "implementation|native"
  [IO.File]::WriteAllBytes("$env:SHIPCHK\vault\alpha\raw.bin", [byte[]](1..32))
  dazzlesum create "$env:SHIPCHK\vault\alpha"
  certutil -hashfile "$env:SHIPCHK\vault\alpha\raw.bin" SHA256
  Select-String -Path "$env:SHIPCHK\vault\alpha\.shasum" -Pattern "raw.bin"
  ```
- [ ] **Expected:** The `-vvvv` log says `Using Python implementation for sha256` -- native tools are fallback-only since the engine-order flip (they cost a per-file subprocess spawn AND hash raw bytes, bypassing line-ending normalization). The `.shasum` digest for `raw.bin` must equal certutil's -- binary files are never normalized, so the two engines must agree byte-for-byte there. Do NOT expect agreement on text files with CRLF line endings: normalization of those is intentional dazzlesum behavior.

### 3.2 fsum banner-on-stderr case (only if fsum 2.51 is installed)

- [ ] **Steps**: `python -c "from dazzlesum.hashing import DazzleHashCalculator; print(DazzleHashCalculator()._tool_available('fsum'))"`
- [ ] **Expected:** `True` when fsum is on PATH (its banner goes to stderr with a nonzero rc -- the second half of the U4 fix). Skip if fsum is not installed.

### 3.3 Absent tool degrades silently to Python hashing

- [ ] **Steps**: `python -c "from dazzlesum.hashing import DazzleHashCalculator; print(DazzleHashCalculator()._tool_available('no-such-tool-xyz'))"`
- [ ] **Expected:** `False`, instantly, no traceback, no console noise.

### 3.4 POSIX parity (if a POSIX box is available)

- [ ] **Steps**: repeat 3.1 with `shasum`/`sha256sum`; compare a `.shasum` produced on Windows against one produced on POSIX for the same fixture bytes.
- [ ] **Expected:** Identical digests (newline normalization in the Python fallback and native paths agree).

- [ ] **Steps**: covered by HV.5; additionally try `//server/share/x` (forward-slash UNC) and a long-prefix path `\\?\C:\x`.
- [ ] **Expected:** Forward-slash UNC -> True. Long-prefix local drive -> False (it is not a network path). Document any surprise rather than "fixing" it ad hoc -- classification comes from filekit.

### 4.2 Real share smoke (optional -- skip if no test share)

- [ ] **Expected:** Same behavior as a local path; no crashes from the filekit layer. Never point this at a production share.

## Section 5: Regression spot-checks (~10 min)

The deep sweep for the v1.5.0 engine lives in `v1.4.4__Epic__snappy-update-verification.md`; these are quick confidence checks that the split didn't disturb behavior.

### 5.1 Update mode incremental behavior

- [ ] **Steps** (PowerShell):
  ```powershell
  dazzlesum create "$env:SHIPCHK\vault" -r
  "changed" | Set-Content "$env:SHIPCHK\vault\alpha\one.txt"
  dazzlesum update "$env:SHIPCHK\vault" -r
  dazzlesum verify "$env:SHIPCHK\vault" -r
  ```
- [ ] **Expected:** update re-hashes only the changed file's folder; verify then reports all OK, exit 0.

### 5.2 Verify failure is loud and exit-coded

- [ ] **Steps**: corrupt a file AFTER create (append a byte), run verify.
- [ ] **Expected:** The mismatched file is named in output; exit code is nonzero. Error wording should tell a human what to do, not just dump a hash pair.

### 5.3 Junction quick check (Windows)

- [ ] **Steps** (PowerShell):
  ```powershell
  New-Item -ItemType Junction -Path "$env:SHIPCHK\vault\loop" -Target "$env:SHIPCHK\vault" | Out-Null
  dazzlesum create "$env:SHIPCHK\vault" -r
  Remove-Item "$env:SHIPCHK\vault\loop"
  ```
- [ ] **Expected:** No infinite recursion, no hang; junction skipped per policy; the real subtree still fully processed (the alpha.1 coverage-hole fix).

### 5.4 Monolithic mode roundtrip

- [ ] **Steps**: `dazzlesum create "$env:SHIPCHK\vault" -r --mode monolithic` then `dazzlesum verify "$env:SHIPCHK\vault"`.
- [ ] **Expected:** Single manifest at the root; verify auto-detects monolithic mode and passes.

### 5.5 Per-file hashing speed sanity (the engine-order regression guard, by feel)

- [ ] **Steps**: run `dazzlesum create <this repo's checkout> -r` and watch the wall clock (delete the generated `.shasum` files afterwards -- they are gitignored but tidy up anyway).
- [ ] **Expected:** A ~130-file tree completes in about a second, not tens of seconds. Sustained ~75ms-per-file pacing is the native-first symptom (one subprocess spawn per file) and is a FAIL: it means the engine order regressed to native-first.

## What the automated tests DON'T cover

- **Real native-tool stream/exit-code behavior**: the U4 bug lived for months precisely because tests mocked `subprocess.run` -- the mocks encoded the same wrong assumption the code made. Only running against real certutil/fsum/shasum (Sections HV.3, 3.x) proves detection.
- **True self-containment of the artifact**: automated runs import the artifact in an environment where the libs ARE installed, so a leaked import would still resolve. Only the bare-venv test (HV.2) proves it.
- **Real UNC shares**: filekit's network-path handling against an actual server (4.2).
- **Isolated-build-env packaging**: `python -m build` inside its own venv (1.1) -- the alpha.4 failure mode.
- **Shell rendering**: output readability on Windows codepage 437/1252 terminals, line wrapping, `-vv` log legibility.
- **Cross-platform digest parity** from real tools on real filesystems (3.4).
- **Error message quality** as judged by a human (5.2).
- **Performance feel** -- covered quantitatively in the v1.4.4 Epic checklist; here only "nothing feels newly slow."
